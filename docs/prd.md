# 사내 마켓 PRD 초안

작성일: 2026-11-04. 논의 결과를 반영한 초안이다. **제안**은 아직 확정되지 않은 설계·운영 선택을 뜻한다.

관련 문서: [ERD](erd.md), [API 명세](api-spec.md), [용어집](../CONTEXT.md).

## 1. 목적과 범위

한 회사의 재직자 약 100명이 물품과 서비스를 거래하는 PC·모바일 반응형 웹이다. 물품과 서비스를 모두 **상품**으로 취급한다. 가격 0원은 나눔이며 별도 상품 유형을 두지 않는다.

포함: 구글 사내 계정 로그인, 개인정보 등록, 상품 승인·공개·수정, 수량 관리, 익명 문의, 거래 신청·수락·완료, 거절 알림, 인사팀 운영.

제외: 플랫폼 결제, 에스크로, 배송 처리, 수락 후 취소, 카테고리, 태그, 별점, 신고, 상품 정보 버전·스냅샷, 웹소켓, 고정 15초 폴링. 결제·전달·서비스 제공은 당사자가 직접 처리한다.

## 2. 사용자와 개인정보

| 역할 | 권한 |
|---|---|
| 재직자 | 상품 조회·등록, 문의·신청. 자신의 상품에서는 판매자 |
| 판매자 | 자기 상품 수정·수량 조정·모집 종료, 신청 수락·거절, 거래 완료 |
| 인사팀 운영자 | 상품 승인·반려, 성사 전 신원 열람, 기간별 거래 완료 금액 조회 |

- 구글 사내 메일로 인증한다. 회사 도메인 실제 값은 미정이다.
- 가입자가 실명·부서·직급을 직접 입력한다. 부서·직급은 회사가 정의한 enum을 드롭다운으로 선택한다. 실제 목록은 미정이다.
- 퇴사 시 구글 계정은 정지된다. 정지 감지 경로와 기존 앱 세션 회수 시점은 미정이다. 계정 정지가 로컬 세션을 즉시 만료시키는 것으로 가정하지 않는다.
- **제안:** 구글 인증 + 서버 세션. 모든 업무 요청에서 로컬 이용 상태를 검사한다. 계정 정지 연동과 세션 유효기간은 도입 환경 확인 후 결정한다.

## 3. 상품 등록·승인

| 항목 | 규칙 |
|---|---|
| 제목·본문 | 필수 |
| 단가 | 원화 정수, 0 이상, 1개 기준 |
| 수량 | 물품·서비스 모두 필수, 등록 시 양의 정수 |
| 사진 | 선택 |
| 수량 단위 | 별도 필드 없음. 판매자가 제목·본문에 설명 |

- 등록 시 PENDING. 인사팀 승인 후 APPROVED가 되어 장터에 공개된다.
- 반려 시 REJECTED와 사유를 제공한다. 판매자는 수정 후 다시 승인 요청한다.
- 승인 후 수정은 재승인하지 않는다.
- 삭제는 장터에서 숨기는 방식이며 기존 쪽지·거래 기록을 유지한다.
- **제안:** 장터는 승인·비삭제 상품을 최신순으로 제공하고 제목·본문 키워드 검색을 지원한다. 모집 종료·수량 소진 상품도 상태를 표시해 조회할 수 있다.
- 사진 개수·크기, 제목·본문 길이, 단가·수량 상한은 미정이다. 최소 1억 원 단가를 지원해야 한다.

## 4. 수량과 모집

- 사과 판매·영어 과외 모두 같은 수량 모델이다. 과외 수량의 의미 등은 판매자가 설명한다.
- 구매자는 신청 수량을 지정한다. 신청만으로 수량을 확보하거나 차감하지 않는다.
- 판매자가 수락할 때 신청 수량만큼 차감한다. 동시 수락에서도 잔여 수량 미만으로 내려갈 수 없다.
- 잔여 수량 0이면 새 신청을 차단한다. 기존 신청도 잔여 수량이 충분해야 수락할 수 있다.
- 판매자는 잔여 수량을 증감할 수 있으나 0 미만은 불가하며 성사된 거래 수량에는 영향이 없다.
- 판매자 모집 종료는 새 신청만 막고 기존 문의·거래는 유지한다.
- 수량 소진만으로 차단된 상품은 수량 추가 시 새 신청이 가능하다. 직접 모집 종료한 상품은 별도로 재개해야 한다.
- **제안:** 새 신청·신청 수량 수정도 현재 잔여 수량 이하로 제한한다. 여러 대기 신청의 합계는 잔여 수량을 초과할 수 있다.

## 5. 거래 흐름

| 상태 | 의미 | 허용 동작 |
|---|---|---|
| REQUESTED | 수락 전 신청 | 구매자 수량 수정·철회, 판매자 거절·수락 |
| WITHDRAWN | 구매자 철회 | 종료 |
| REJECTED | 판매자 거절 | 종료, 신청자 알림 |
| ACCEPTED | 판매자 수락으로 거래 성사 | 판매자가 완료 처리 |
| COMPLETED | 실제 거래 후 판매자가 완료 처리 | 종료 |

- 수락 후 취소는 없으며 구매자의 완료 확인도 없다.
- 수락 전 구매자가 기존 신청 수량을 수정할 수 있다.
- **제안:** 동일 상품·구매자의 진행 중 신청·거래(REQUESTED, ACCEPTED)는 하나. 철회·거절·완료 후 재신청 가능.
- 수락 시 **확정 단가·확정 수량만 거래에 저장**한다. 신청 당시 상품 제목·본문·사진·가격 버전·스냅샷은 저장하지 않는다.
- 상품을 수정해도 확정 단가·수량은 유지한다. 합계는 두 값의 곱으로 계산한다.
- 최초 신청 일시와 최근 신청 수량 수정 일시를 판매자에게 표시한다.
- 수락·수량 수정·재고 조정이 경합하면 최신 상태를 확인하고 하나씩 반영한다.

## 6. 상품 수정과 신청 거절

- 제목·본문·사진·단가를 수정하려면 REQUESTED 신청을 모두 거절한다. 거절된 신청자마다 알림을 보낸다.
- ACCEPTED 거래는 완료 전이어도 상품 수정을 막지 않는다. COMPLETED도 수정 제한 대상이 아니다.
- 거절·알림 생성·상품 수정은 함께 확정한다. 그 사이 새 신청이 들어와 이전 정보에 대한 신청이 남지 않도록 한다.
- 수량 변경은 신청 거절 없이 처리한다. 잔여 수량보다 큰 기존 신청도 자동 거절하지 않으며, 수락 시 잔여 수량을 다시 검사한다. 모집 종료·재개도 기존 신청을 유지한다.
- **제안:** 일반 수정은 대기 신청이 있으면 차단하고, 판매자가 명시적으로 ‘대기 신청 모두 거절 후 수정’을 선택하면 한 번에 처리한다.

## 7. 익명과 신원 공개

- 성사 전 상대의 실명·부서·직급을 공개하지 않는다. 인사팀은 열람할 수 있다.
- 판매자는 ‘판매자’, 구매자는 상품별 신청 순서에 따라 ‘익명 1’, ‘익명 2’로 표시한다.
- 신청 전 문의는 ‘문의자 A’ 등으로 표시한다. 신청 후 신청 순번 별칭으로 전환하고 기존 대화는 유지한다.
- 성사 시 해당 두 사람에게만 실명·부서·직급을 공개한다. 다른 신청자에게는 공개하지 않는다. 이메일은 공개하지 않는다.
- 다른 상품의 같은 사람을 연결하는 전역 사용자 ID·프로필 링크는 제공하지 않는다.
- **제안:** 재신청해도 상품 내 별칭은 유지하고 순번은 재사용하지 않는다. 같은 상품에서 이미 성사된 두 사람의 신원 공개는 유지한다.
- 시스템이 표시하는 신원을 통제한다. 사용자가 본문·사진·쪽지에 직접 적은 개인정보를 자동 차단하는 기능은 범위에 없다.

## 8. 쪽지·알림

- 문의와 거래 신청은 별개다. **제안:** 상품별 판매자–구매자 1:1 텍스트 쪽지함을 사용한다.
- 웹소켓·고정 주기 폴링 없이 쪽지함 진입·수동 새로고침 시 내용을 조회한다.
- 기존 인증 갱신·일반 API 응답에 미확인 쪽지 여부를 함께 전달한다. 요청이 없으면 새 쪽지가 즉시 표시되지는 않는다.
- **제안:** 쪽지에 수신 사용자·읽음 시각을 저장하고 미확인 여부를 조회한다. 사용자 테이블 카운터나 토큰 내 미확인 값은 두지 않는다.
- 신청 거절 알림은 앱 내 알림함에 저장한다. 기존 응답에 미확인 알림 여부를 포함하고 읽음은 별도 요청으로 처리한다. 외부 이메일·구글 챗 발송은 포함하지 않는다.

## 9. 인사팀 거래 완료 통계

- 인사팀은 시작일·종료일을 선택해 총 거래 완료 금액을 조회할 수 있다. 일반 사용자에게는 제공하지 않는다.
- 합계는 COMPLETED 거래의 `확정 단가 × 확정 수량`을 더한다. 신청·거절·철회·성사 후 미완료 거래는 제외하고, 같은 거래를 한 번만 합산한다.
- 기준 시각은 판매자의 완료 처리 시각 completed_at이다. 상품 현재 가격·수정·숨김에 영향을 받지 않는다.
- **초안 기본값:** Asia/Seoul 날짜 기준 시작일·종료일 모두 포함. 서버는 시작일 00:00 이상, 종료일 다음 날 00:00 미만의 UTC 구간으로 변환한다.
- 결과는 총액(KRW)과 완료 거래 건수. 나눔도 거래 건수에는 포함하되 금액은 0이다. 결과가 없으면 금액·건수 모두 0이다.
- 이는 판매자 완료 표시 기준 장터 거래액이며 실제 송금 검증이나 회사 매출·결제 정산 자료가 아니다.

## 10. 비용·운영 제약

- 기술 스택의 최우선 기준은 최소 운영 요금과 운영 부담이다. 약 100명 규모에 맞추고 상시 프로세스·메모리·별도 DB 서버를 최소화한다.
- 업무 API와 정적 화면을 분리하고 필요한 요청만 처리한다. 실시간 연결·정기 폴링·상시 백그라운드 작업·별도 통계 서버는 두지 않는다.
- 통계는 인사팀 조회 시 인덱스로 범위를 제한해 SQL 합산하며 별도 통계 저장소·정기 집계를 도입하지 않는다.
- 사진은 업로드 전 브라우저에서 축소·압축하는 방향으로 제안한다. 저장량·이미지 조회 요청·API CPU·DB 읽기/쓰기량을 함께 관리한다.
- [저비용 기술 스택 제안](tech-stack.md)을 별도 기록한다. Railway 사용량 기반 요금과 개발·운영 시간을 함께 최소화한다. 실제 사용량 측정 전 월 요금을 보장하지 않는다.

## 11. 인수 조건

1. 미승인 상품은 장터·일반 사용자 직접 URL 조회에 노출되지 않는다.
2. 익명 응답에 상대의 전역 사용자 ID·이메일·실명·부서·직급이 없다.
3. 잔여 수량 3에서 수량 2 신청 두 건을 동시 수락하면 하나만 성공하고 잔여 수량은 1이다.
4. 일괄 거절 후 상품 수정은 거절·신청자 알림·수정이 전부 성공하거나 전부 실패한다.
5. 성사된 미완료 거래가 있어도 상품 수정 가능하며 해당 거래 확정 단가·수량은 유지된다.
6. 구매자의 신청 수량 수정 시 판매자는 최신 수량과 수정 시각을 확인한다.
7. 모집 종료는 기존 거래·쪽지를 삭제하지 않으며 수량 추가만으로 해제되지 않는다.
8. 거절 알림은 해당 신청자만 조회하고, 인사팀 외 제삼자는 미성사 신원을 조회할 수 없다.
9. 수량 변경 시 대기 신청·거래는 유지되며 거절 알림이 생성되지 않는다.
10. 인사팀 기간 조회는 완료 시각으로 필터링하고 확정 단가·수량으로 합산한다. 미완료는 제외하고 종료일 마지막 시각의 거래는 포함한다.

## 12. 미정·최종 확인

- 회사 도메인, 부서·직급 목록, 관리자 지정 방식, 계정 정지 감지·세션 회수.
- 중복 진행 거래 제한, 재신청 별칭 유지 등 남은 제안 사항. 수량 변경의 거절 예외와 앱 내 알림함은 확정했다.
- 사진·본문·금액·수량 제한, 개인정보·쪽지·거래 보관 및 탈퇴 정책.
- 성사 후 실제 거래가 이행되지 않을 때 운영 처리. 사용자 취소 기능은 추가하지 않는다.
- 개인정보 변경 가능 범위와 성사 상대에게 보여줄 개인정보의 기준 시점.

## 확정된 가입·부서 운영 (#31)

구글 로그인은 메일 도메인 제한 없이 허용한다. 최초 로그인 후 실제 이름·부서·직급을 입력하여 가입을 신청하며, 인사팀 승인 전에는 장터를 이용할 수 없다. 부서는 초기 인사팀만 제공하고 관리자가 추가·이름 변경·미사용 일반 부서 삭제를 수행한다. 직급은 서버가 제공하는 고정 선택 목록을 사용한다. 인사팀 선택자도 승인 전에는 관리자 권한이 없고 승인 시에만 관리자 권한을 받는다. 관리자는 가입 승인·반려·이용 정지·정지 해제를 처리한다. 최초 관리자는 실제 로그인 후 인사팀으로 가입 신청한 사용자를 운영자가 정확한 이메일로 DB 승인한다. 첫 로그인 자동 관리자 지정은 하지 않는다.
