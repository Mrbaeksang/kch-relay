# 공통 개발 기반 명세 초안

2026-11-04. 상태: 2026-11-05 공통 기반 구현·검증 완료, 운영 배포 전. 대화에서 확정한 방향과 이 문서가 새로 제안하는 세부 기본값을 구분한다. 공통 기반 6개 티켓을 구현했다. 상품·거래 등 업무 기능은 후속 작업이다. 구체적인 공급·소비 계약은 별도의 공통 기반 계약 v1을 따른다.

## Problem Statement

6명이 같은 사내 마켓을 개발할 때 인증·오류·DB·라우트·디자인 기반을 각각 만들면 연결 단계에서 재작업이 생긴다. 구글 콘솔 계정 발급 전에도 관리자·직원 권한과 실제 거래 흐름을 개발할 수 있어야 한다. 프로젝트 소유자는 초기 프론트 디자인 기조를 직접 정하며, 다른 구성원은 그 결과를 기다리는 동안에도 기능 개발을 진행할 수 있어야 한다.

작성 시작 당시 준비된 것은 정적 준비 화면, Go 서버, SQLite 사용자 초기 스키마·마이그레이션, 상태 확인, 단일 Docker·영구 볼륨 검증, CI다. 업무 API·인증·세션·전체 업무 스키마는 아직 구현되지 않았다.

## Solution

구글 인증보다 먼저 환경설정·서버 세션·개발 로그인·공통 API·전체 초기 스키마·모듈 연결·테스트 데이터를 준비한다. 이후 모든 기능은 동일한 인증 사용자와 데이터 계약 위에서 화면부터 DB까지 구현한다. 운영은 단일 Go 프로세스로 화면과 API를 제공하고, 개발은 Vite와 Go를 나누어 실행한다.

공통 기반은 팀원이 테스트 관리자로 로그인하고 관리자 전용 확인 화면에 접근한 뒤, 테스트 직원으로 전환하면 접근이 거절되는 흐름까지 실제 HTTP와 SQLite로 검증되어야 한다. 업무 상품·거래 기능을 미리 구현하거나 완성된 것처럼 표시하지 않는다.

## User Stories

1. 개발자로서, 같은 명령과 환경설정으로 실행하여 개인마다 다른 환경 문제를 줄이고 싶다.
2. 개발자로서, 잘못된 환경설정을 시작 시 확인하여 실행 후 원인을 찾는 시간을 줄이고 싶다.
3. 개발자로서, 구글 자격 증명 없이 테스트 계정을 선택하여 기능을 개발하고 싶다.
4. 개발자로서, 테스트 관리자로 로그인하여 승인·통계 등 관리자 권한을 검증하고 싶다.
5. 개발자로서, 테스트 직원 A와 B를 사용하여 판매자·구매자 간 동작을 확인하고 싶다.
6. 개발자로서, 로그인 상태가 새로고침 후 유지되어 실제 사용 흐름을 검사하고 싶다.
7. 개발자로서, 로그아웃·세션 만료·이용 정지가 실제로 접근을 차단하는지 확인하고 싶다.
8. 운영 담당자로서, 운영에서 테스트 로그인이 열리지 않아 가상 관리자로 접근되는 일을 막고 싶다.
9. 기능 담당자로서, 로그인 방식과 무관한 동일 사용자 정보를 받아 구글 인증 전환 시 재작업을 줄이고 싶다.
10. 기능 담당자로서, 공통 API 오류 형식을 받아 입력 오류·권한 거절·상태 충돌을 일관되게 안내하고 싶다.
11. 기능 담당자로서, 공통 권한 검사와 별도 소유권 검사의 차이를 알고 타인의 데이터가 노출되지 않게 만들고 싶다.
12. 기능 담당자로서, 같은 초기 스키마·제약을 사용하여 다른 사람의 마이그레이션 완료를 기다리지 않고 개발하고 싶다.
13. 기능 담당자로서, 트랜잭션 안에서 수량·거래·알림을 함께 변경하여 부분 반영을 막고 싶다.
14. 쪽지 담당자로서, 거래 신청과 같은 상품별 익명 연결을 사용하여 별칭과 대화가 중복되지 않게 하고 싶다.
15. 알림 담당자로서, 거래 담당자가 합의된 알림 생성 계약을 사용하여 알림함을 독립적으로 구현할 수 있기를 원한다.
16. 통계 담당자로서, 완료 거래 테스트 데이터로 기간 집계를 검증하여 거래 화면 완성을 기다리지 않고 싶다.
17. 프론트 담당자로서, 같은 API 호출·인증 상태·라우트 연결을 사용하여 공통 설정 충돌을 줄이고 싶다.
18. 프로젝트 소유자로서, 공통 UI의 색상·글꼴·간격·컴포넌트 기조를 먼저 정하고 이후 화면에 적용하고 싶다.
19. 다른 프론트 담당자로서, 디자인 확정 전에도 기본 마크업으로 화면 동작을 연결하고 싶다.
20. 팀원으로서, 필요한 공용 변경의 담당자를 알아 다른 사람이 동시에 같은 기반을 수정하는 일을 줄이고 싶다.
21. 개발자로서, 격리된 테스트 DB와 가상 데이터를 사용하여 다른 테스트나 내 로컬 데이터를 훼손하지 않고 싶다.
22. 운영 담당자로서, 재배포 후에도 DB와 사진이 남는지 검사하고 싶다.

## Implementation Decisions

### 1. 확정 방향

- 모노레포, Vite·React·TypeScript, Go·chi, SQLite·modernc·goose를 유지한다.
- 운영은 단일 Docker 이미지·Go 프로세스·Railway 서비스·영구 볼륨이다. 프론트 정적 파일과 API를 Go가 함께 제공한다. 별도 Node·S3·DB 서버를 추가하지 않는다.
- 개발은 Vite 5173과 Go 8080, 운영 기본 내부 포트는 8080이다. 운영 외부 HTTPS 포트는 Railway가 처리하며 PORT 주입을 존중한다.
- 테스트 관리자 1명과 직원 A·B를 사용한다. 구글 인증은 콘솔 자격 증명 발급 후 별도 작업으로 연결한다.
- 프로젝트 소유자가 공통 기반과 초기 프론트 디자인 기조를 담당한다. 본 단계에서 디자인 방향을 임의로 확정하지 않는다.
- 테스트의 주 경계는 실제 HTTP 요청과 임시 SQLite이며 프론트는 사용자 행동을 검사한다.

### 2. 기능별 단일 서버 구조

DDD의 용어 일관성과 업무 규칙 경계는 사용하되, 모든 기능에 엔티티·리포지토리 인터페이스·도메인 이벤트 계층을 강제하지 않는다. 모듈 내부는 HTTP 처리 → 업무 처리 → 명시적 SQL로 시작한다.

| 모듈 | 책임 | 소유하지 않는 것 |
|---|---|---|
| 인증·회원 | 로그인 수단, 사용자 조회, 세션 발급·회수, 역할·활성 상태 | 상품별 신원 공개 판단 |
| 마켓 | 상품·승인·신청·거래·수량의 변경과 원자성 | 쪽지·알림함 UI, 통계 UI |
| 상품별 참여 연결 | 구매자별 대화 연결, 별칭 순번, 신원 공개 시각 | 일반 공개 사용자 프로필 |
| 쪽지 | 대화 내용·읽음·수신 권한 | 신청 수락·상품 가격 변경 |
| 알림 | 같은 트랜잭션의 거절 알림 저장, 알림함·읽음 | 거래 상태 판단 |
| 통계 | 완료 시각·확정 단가·수량의 읽기 전용 집계 | 거래 완료 상태 변경 |

마켓은 상품과 거래를 같은 업무 변경 경계 안에 둔다. 상품 담당과 거래 담당은 화면·유스케이스를 나눌 수 있으나, 서로 다른 모듈에서 같은 수량·수락·일괄 거절 규칙을 중복 구현하지 않는다. 6명이라고 백엔드 패키지를 반드시 6개로 맞추지 않는다.

모듈 연결은 서버 조립 지점에서 한다. 공통 응답 모듈이 쪽지·알림 기능을 직접 import하지 않고, 미확인 여부 조회 기능을 조립 시 주입하여 순환 의존을 피한다. 테스트 교체가 필요한 곳이나 모듈 경계에만 작은 인터페이스를 사용한다.

### 3. 환경설정과 시작 순서 — 제안

| 설정 | 기본값·정책 |
|---|---|
| APP_ENV | production. 로컬 개발은 development를 명시 |
| AUTH_MODE | disabled. 개발 시 development를 명시, 추후 google 지원 |
| PORT | 8080 |
| DATABASE_PATH | 로컬 가상 데이터 위치, 운영은 영구 볼륨 내 DB |
| UPLOAD_DIR | 로컬 업로드 위치, 운영은 영구 볼륨 내 uploads |
| WEB_DIR | 빌드된 프론트 정적 파일 위치 |
| APP_ORIGIN | 브라우저가 사용하는 신뢰할 앱 주소. 운영 HTTPS, 개발은 Vite 주소 |
| SESSION_TTL | 개발 초기값 8시간. 운영 정책은 구글 인증 작업에서 재확정 |

환경설정은 시작 시 한 번 읽어 타입·값·조합을 검증하고 각 모듈에 전달한다. 업무 처리 중 환경변수를 개별 조회하지 않는다. 개발 편의를 위한 dotenv 자동 로딩은 기본으로 추가하지 않는다.

운영 환경과 개발 인증 모드의 조합은 시작 오류다. disabled에서는 개발 로그인 경로·가상 계정 생성이 없으며 업무 API는 인증 없이는 접근할 수 없다. 아직 지원하지 않는 google 모드를 지정하면 명확히 시작 실패하고 개발 인증으로 대체하지 않는다. 임의 localhost·다른 서비스 도메인을 허용하는 전체 CORS는 사용하지 않는다. 개발 요청은 Vite 프록시를 사용한다.

시작 순서는 설정 검증 → 저장 위치 준비 → DB 연결·마이그레이션 → 개발 모드일 때만 가상 사용자 보장 → 모듈 조립 → HTTP 시작이다. 중요 설정·마이그레이션이 실패하면 정상 준비 상태를 반환하지 않는다.

### 4. 테스트 로그인과 세션 — 제안

| 가상 사용자 | 역할 | 용도 |
|---|---|---|
| 테스트 관리자 | HR_ADMIN | 상품 승인·반려·신원 열람·통계 |
| 테스트 직원 A | MEMBER | 상품 판매 또는 구매 |
| 테스트 직원 B | MEMBER | 상대방 거래·쪽지·익명성 확인 |

- 고정된 내부 가상 사용자 키로 멱등 생성한다. 재시작 시 신규 사용자를 중복 생성하거나 기존 거래 데이터를 초기화하지 않는다. 이메일은 example.invalid의 가상 값만 사용한다.
- 실제 부서·직급 목록과 구글 사용자 식별자가 아직 없으므로 개발 값은 명시적으로 가상 값으로 구분한다. 가짜 google_subject를 실제 인증 연결 키처럼 사용하지 않는다.
- 기존 users의 google_subject 필수 제약은 추가 마이그레이션으로 nullable·고유로 변경하는 방향을 제안한다. 개발 사용자는 null이며, 나중에 검증된 구글 계정 연결 시 실제 subject를 기록한다. 기존 적용 마이그레이션을 덮어쓰지 않는다.
- 브라우저는 가상 사용자 키만 보낸다. 임의 userId·role을 받아 로그인시키는 API를 만들지 않는다.
- 로그인은 실제 서버 세션을 발급한다. 화면에서만 역할을 바꾸거나 요청 헤더의 사용자 ID를 신뢰하는 모킹을 사용하지 않는다.
- 토큰은 암호학적 난수로 생성하고 서버에는 해시만 저장한다. 쿠키는 HttpOnly, SameSite=Lax, 운영은 Secure다. 토큰은 응답 본문·localStorage·로그에 남기지 않는다.
- 로그인 교체 시 현재 브라우저 세션을 회수하고 새로 발급한다. 각 브라우저 프로필·기기 세션은 별개다. 같은 브라우저 탭 두 개는 쿠키를 공유하므로 A/B 동시 검증에는 별도 프로필을 사용한다.
- 모든 업무 요청에서 세션 만료·회수 및 사용자 ACTIVE 상태를 확인한다. 로그아웃은 서버 세션을 회수한다. 요청마다 만료를 연장하는 쓰기는 하지 않는다.
- 변경 요청은 신뢰할 Origin 검사와 세션에 연결된 CSRF 토큰을 검증한다. 개발 로그인·구글 콜백처럼 세션 생성 전인 경로는 별도 검증 정책을 적용한다.

### 5. 공통 인증 API 계약 — 제안

모든 업무 API는 기존 명세의 버전 접두어를 유지한다.

| API | 동작 |
|---|---|
| GET auth/config | 인증 모드·개발 로그인 제공 여부. 개발일 때만 선택 가능한 가상 계정 표시 |
| POST auth/development-login | 허용된 가상 계정 키로 세션 발급, development에서만 경로 등록 |
| GET auth/me | 본인 ID·실명·부서·직급·역할·상태, CSRF 토큰, 미확인 쪽지·알림 표시 |
| POST auth/logout | 현재 세션 회수·쿠키 제거 |

구글 로그인·가입은 이번 기반에 미구현 상태로 명확히 남긴다. 인증 수단은 나중에 동일한 세션 발급 기능을 호출한다. 8시간 고정 세션을 사용하는 동안 불필요한 refresh API는 구현하지 않는다. 기존 초안의 refresh 경로는 필요성이 생길 때 다시 확정한다.

### 6. 공용 기능의 최소 목록 — 제안

이름은 책임을 합의하기 위한 제안이며 최종 구현 시 Go 관례에 맞춘다. 전역 변경 가능 변수와 범용 utils 모음은 만들지 않는다.

| 기능 | 계약 |
|---|---|
| LoadConfig | 환경설정 읽기·검증. 시작 시 한 번 |
| DecodeJSON | 본문 크기·JSON 형식·알 수 없는 필드 검증. 필드 업무 규칙은 각 기능이 검증 |
| WriteSuccess / WriteError | 공통 응답 형식·상태 코드·안전한 오류 메시지 |
| CurrentUser / RequireUser / RequireAdmin | 검증된 현재 사용자 전달, 인증·역할 확인. 소유권 판단은 업무 기능 책임 |
| NewID / NowUTC | 식별자·시각 생성. DB/업무 서비스에 필요할 때 주입해 결정적 테스트 지원 |
| WithTx | 같은 SQLite 트랜잭션으로 여러 변경 실행, 실패 시 rollback, 성공 시 commit |
| ParsePage | 공통 cursor·limit 검증. 각 목록이 정렬 기준과 접근 범위를 결정 |
| ParseDateRange | KST 날짜 범위를 UTC 반열린 구간으로 변환 |
| AppendRejectionNotificationTx | 전달받은 트랜잭션에서 거절 알림 저장, 거래당 중복 방지 |
| EnsureParticipantTx | 동일 상품·구매자 연결 재사용, 별칭 번호 배정의 원자성 보장 |

세션이나 익명 상대를 표현하는 공통 타입에는 필요한 값만 둔다. 익명 상품 응답에 사용자 내부 모델을 직접 직렬화하지 않는다.

### 7. 응답·오류·미확인 표시 — 제안

- 성공은 data와 meta, 오류는 error와 필요한 meta. 목록은 items와 nextCursor다.
- 업무 오류는 400 입력 오류, 401 인증 만료, 403 역할·이용 제한, 404 비공개/없는 리소스, 409 상태·수량 충돌로 통일한다. SQL 오류·내부 경로·비밀값은 응답에 포함하지 않는다.
- 인증된 일반 JSON 업무 응답에는 hasUnreadMessages와 hasUnreadNotifications를 포함한다. 헬스 체크·리다이렉트·사진 파일 등은 제외한다.
- 미확인 표시는 사용자별 인덱스 기반 EXISTS로 조회하고 전체 COUNT를 반복하지 않는다. 요청당 한 번만 조회하며 쪽지·알림 읽음/생성 동작에서는 변경 후 결과를 반환한다.
- 알림 정보 조회 실패를 ‘없음=false’로 숨기지 않는다. 해당 응답은 서버 오류로 처리한다. 상태 변경은 이미 commit됐을 수 있으므로 변경 결과 재조회·멱등성으로 재시도를 처리한다.
- 프론트는 공통 API 호출에서 메타를 받아 표시를 갱신한다. 요청이 없는 동안 즉시 도착을 보장하지 않으며 폴링을 추가하지 않는다.
- 페이지 크기는 기본 20·최대 100을 제안한다. 실제 정렬 키는 시각과 불투명 ID를 함께 사용한다.

### 8. DB·공통 스키마·트랜잭션 — 제안

- SQLite 외래키 활성화, 연결 수 1, busy timeout 5초로 시작한다. WAL은 측정 없이 기본 추가하지 않는다. SQLite에서 SELECT FOR UPDATE를 사용하지 않는다.
- 공통 기반에서 users·sessions·products·participants·deals·messages·notifications·images·reviews의 컬럼·제약·인덱스 계약과 초기 마이그레이션을 준비한다.
- 실제 부서·직급 enum 목록은 미정으로 남긴다. 개발용 code·label만 제공하고 구글 인증 시점에 실제 목록으로 교체·데이터 정리 정책을 정한다.
- 금액·수량·본문·사진 크기 등의 숫자 상한은 기능 티켓 발행 전에 따로 고정한다. 정하지 않은 값을 확정 정책처럼 DB 제약에 넣지 않는다.
- 거래 상태, 잔여 수량 비음수, 합의 필드, 외래키, 상품별 참가자 고유, 중복 거절 알림 방지 등 이미 확정된 제약을 먼저 둔다. 미확정인 진행 중 거래 1건 제한은 정책 확인 후 제약을 확정한다.
- WithTx 안에서는 전달받은 tx로만 쿼리한다. 연결 수 1 상태에서 바깥 DB를 다시 호출해 교착·대기를 만들지 않는다. 트랜잭션 안에서 네트워크·이미지 처리·메일 발송은 하지 않는다.
- 수락은 현재 상태·수량 조건 검사, 재고 차감, 단가·수량 확정, 신원 공개를 함께 확정한다.
- 상품 내용·단가 수정은 대기 신청 거절·알림·수정을 함께 확정한다. 수량 변경은 기존 신청을 유지한다.
- 알림 생성 함수는 전달받은 tx에 쓰기만 한다. 자체 commit·별도 연결을 열지 않는다. 비동기 이벤트 버스·메시지 큐는 추가하지 않는다.
- 적용된 마이그레이션은 수정하지 않고 새 번호를 추가한다. 병렬 구현 전 각 담당 작업에 사용할 후속 마이그레이션 번호를 조정한다.

### 9. 가상 데이터와 테스트 데이터 — 제안

- 서버 시작 시 자동 생성하는 것은 development의 가상 사용자 3명뿐이다. 상품·거래 샘플은 명시적 개발 명령으로 추가하고 사용자 동의 없이 DB를 초기화하지 않는다.
- 공통 테스트 데이터 빌더는 사용자, 승인/대기/반려 상품, 상품별 참여자, 신청/성사/완료 거래, 읽은/안 읽은 쪽지·알림을 생성할 수 있다.
- 빌더는 실제 마이그레이션과 같은 DB 제약을 사용한다. 통계 담당자가 거래 화면을 거치지 않고 완료 데이터를 만들 수 있지만 production 업무 API의 상태 검사를 우회하는 기능을 제공하지 않는다.
- 테스트마다 임시 DB·사진 디렉터리를 분리한다. 전역 DB나 운영 볼륨을 공유하지 않는다.

### 10. 프론트 공통과 디자인 담당 경계 — 제안

- 공통 기반은 API 호출·오류 변환·인증 상태·로그인 가드·관리자 가드·라우트 진입점만 제공한다. 클라이언트 가드는 편의 기능이며 서버 검증을 대체하지 않는다.
- 프로젝트 소유자가 기본 레이아웃, 색상·글꼴·간격, 버튼·입력·상태 안내 등의 초기 기조를 만든다. 이번 공통 명세는 시각 디자인을 확정하지 않는다.
- 다른 담당자는 합의한 컴포넌트 이름·props가 준비되면 사용하고, 그 전에는 기능 검증용 기본 마크업으로 작업한다. 임시 마크업을 최종 디자인 완료로 표시하지 않는다.
- API·인증 상태·라우트·전역 스타일은 공동 수정 지점이므로 담당자 또는 작은 별도 PR로 조정한다. 기능 담당자는 자기 화면·유스케이스 중심으로 변경한다.
- 상품·거래·쪽지·알림·관리자 경로의 이름과 화면 데이터 계약을 먼저 고정한다. 티켓별로 루트 앱·환경설정을 새로 만들지 않는다.

### 11. 병렬 작업을 열기 위한 완료 기준

- 관리자/A/B 선택 로그인과 로그아웃이 실제 세션으로 동작하고 새로고침 후 본인 조회가 된다.
- 직원의 관리자 확인 API 요청은 403, 미로그인은 401, 만료·회수·정지는 접근 차단이다.
- production에서 개발 인증을 켜면 시작 실패하며, 정상 production 모드에는 개발 로그인 경로·가상 사용자 seed가 없다.
- 모든 업무 테이블의 합의된 초기 스키마가 마이그레이션되고 필요한 가상 데이터 빌더가 존재한다.
- 공통 성공·오류·미확인 표시와 프론트 API 호출이 연결된다.
- Docker 재생성 후 데이터가 보존되고 기존 CI가 통과한다.
- 각 담당 영역은 다른 기능 담당자의 미완료 구현 대신 합의된 계약·실제 SQLite fixture로 검증할 수 있다.
- 이는 병렬 개발 착수 조건이다. 운영 전체 동작 완료는 아니며 최종 실제 연결 검증은 별도로 필요하다.

## Testing Decisions

- 주 테스트 경계는 실제 HTTP + 실제 modernc SQLite다. 기존 준비 API·SQLite 재시작 보존 테스트를 확장한다. 내부 함수 호출 순서·SQL 문자열 자체를 주 검증 대상으로 삼지 않는다.
- 정상 인증뿐 아니라 임의 계정 키, 클라이언트 role 위조, 타인 조회, 정지·만료·회수·로그아웃을 검증한다.
- 개발 로그인과 향후 구글 로그인은 같은 세션·CurrentUser 계약을 사용한다. 구글 외부 통신 검증은 이번 범위에서 제외한다.
- 트랜잭션 테스트는 중간 실패 후 모든 변경이 되돌아오는지 실제 조회로 확인한다. 두 동시 요청이 재고를 초과하거나 같은 별칭·알림을 중복 생성하지 않는지 검사할 수 있는 기반을 제공한다.
- 세션 만료·KST 날짜 경계는 통제된 시각을 주입해 검사하고 임의 sleep에 의존하지 않는다.
- 프론트는 계정 선택→로그인 표시→관리자 접근 차단→로그아웃의 사용자 행동과 오류 안내를 검사한다. 공통 API 모킹과 실제 브라우저 연결 검증을 구분한다.
- 기존 프론트·Go·Docker CI를 사용하며 새 로컬·CI 차이가 생기지 않게 한다. 앱 기능과 무관한 테스트 프레임워크를 추가하지 않는다.

## Out of Scope

- 실제 구글 인증·가입·회사 계정 정지 자동 감지, 운영 계정 발급.
- 실제 상품·승인·쪽지·거래·알림함·통계 업무 화면과 전체 API 구현.
- 프로젝트 소유자의 시각 디자인 방향 확정·완성.
- S3·외부 채팅·Redis·별도 Postgres·이벤트 버스·마이크로서비스.
- 자동 운영 배포, 개인정보 보관 기간·법적 정책의 임의 확정.
- 6명용 기능 티켓 발행·구성원 업무 배정. 본 공통 기반 명세 확인 후 수행한다.

## Further Notes

- 본 문서는 새로 제안한 환경 기본값·인증 세부·테이블 변경을 검토 가능하게 만든 것이다. 기존 PRD·ERD·API를 이미 수정한 것으로 보지 않는다. 합의되면 같은 변경에서 기존 문서와 ADR을 맞춘다.
- 현재 개발자별 로그인과 전역 폴더/설정/API 공통 함수를 먼저 준비하며 구글 콘솔 발급을 기다리지 않는다.
- 주의할 실제 결합은 상품별 참여자 공유, 수락 시 수량 정합성, 상품 수정 시 거절 알림이다. 이를 공통 계약과 단일 트랜잭션 경계로 고정한 뒤 티켓 사이의 불필요한 대기를 제거한다.

- 설정·서버 수명주기, 글로벌 HTTP·오류·인증 context, 전체 SQLite schema·tx·fixture, 실제 개발 세션·CSRF, 프론트 API·인증 가드가 연결됐다.
